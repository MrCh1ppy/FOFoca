## Context

The proposal introduces a standalone Python 3 `fofoca-data` project and dedicated PostgreSQL database. The review draft `docs/fofoca-data-v0.1.md` predates the current decision to do historical backfill only. AKShare 1.18.97 `fund_open_fund_info_em(symbol, indicator="单位净值走势")` and `indicator="累计净值走势"` each return all available history without a date argument; their pandas numeric conversion has already lost original decimal precision. ETF/LOF spot feeds fail on the development machine and Aliyun, so selection relies on reachable `fund_name_em` and `fund_open_fund_daily_em` instead. Selection is a pragmatic *current candidate* proxy for NAV-based subscription/redemption on this platform, not proof of off-exchange trading, an archive of formerly tradable funds, or an Alipay inventory.

## Goals / Non-Goals

**Goals:**
- Run on supplied fund codes or discover current candidates, applying identical eligibility checks, fetching all available dated unit and accumulated NAV history per selected fund, and filling missing fields/dates from at most two recent daily-snapshot dates.
- Keep fund-level writes idempotent and atomic with successful sync state; preserve successful funds if another fund fails; make failures visible and retryable.
- Read stored rows by code and inclusive date interval without mutating the database.

**Non-Goals:**
- No daily incremental job, automatic runs, scheduled job/timer, upstream date-range fetch, strict T+1/Alipay guarantee, proof of pure off-exchange trading, historical eligibility inference, or Ariadne integration.
- No use of `fund_etf_fund_info_em` (exchange-traded range API) or ETF/LOF spot feeds. The recent `fund_open_fund_daily_em` snapshot is neither full history nor proof of trading venue.

## Decisions

1. **Selection:** Fetch `fund_name_em()` (code/name/type) and `fund_open_fund_daily_em()` (code, purchase/redemption statuses, recent NAV snapshot). Normalize codes to six-digit strings; intersect the feeds. Require purchase status exactly `开放申购` and redemption status exactly `开放赎回`, and a known non-money-market type from the name directory. Do not filter by fund name containing ETF or LOF, nor by index type: an open-on-both-sides LOF such as `166009` qualifies under this rule, and an ETF with both statuses open may qualify as well. Reject missing/ambiguous required codes, types or statuses rather than inferring eligibility. Daily status is a pragmatic NAV-based subscription/redemption proxy for this platform, not authoritative proof of trading venue or Alipay availability. All-funds and supplied-code modes use the same check; supplied codes outside the set are reported as ineligible, not fetched. Any mandatory feed request or unparseable required schema fails closed before selecting/backfilling in either mode; never proceed with a partial catalog. Do not depend on `fund_purchase_em`, `fund_etf_spot_em`, or `fund_lof_spot_em`. Report feed sizes, intersection, status/type exclusions, final candidates and explicitly ineligible codes in a fixed filter order without double-counting.
2. **Retrieval and merging:** Process one fund at a time and request the two `fund_open_fund_info_em` indicators independently, without date filters. Normalize actual returned calendar dates and finite positive NAV values, then outer-join by date. Also parse the selected fund's daily-snapshot columns named `YYYY-MM-DD-单位净值` and `YYYY-MM-DD-累计净值`: discover actual valid dates from column names, use at most the two latest distinct dates present (never assume today's date or positional columns), and map each value to its column's date and metric. A missing snapshot metric stays missing. For each date/metric, full-history data takes precedence; use a snapshot value only when history has no value for that date/metric, including an absent historical date. Report differing non-NULL history/snapshot values on the same date/metric without overwriting history. A failed indicator request, invalid nonempty history response, or both indicators empty fails that fund rather than treating the snapshot as full history; one valid empty indicator and one nonempty indicator records `SUCCESS` while reporting partial historical coverage. Malformed dated snapshot columns or invalid present snapshot NAV for a selected fund fail that fund rather than inventing or silently dropping data. Alternative (using stored last date as upstream cursor) cannot reduce history requests with this API. Convert provider numeric values with `Decimal(str(value))`, round to six fractional digits using `ROUND_HALF_UP`, and reject overflow beyond `NUMERIC(18,6)`; this is a reproducible storage policy, not recovery of original decimals.
3. **Persistence:** In the standalone database, use `fund(id BIGSERIAL PRIMARY KEY, code VARCHAR(16) UNIQUE, name VARCHAR(128), fund_type VARCHAR(64), status VARCHAR(16) DEFAULT 'ACTIVE', established_date DATE NULL, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ)`; `fund_nav_daily(fund_id BIGINT REFERENCES fund(id), nav_date DATE, unit_nav NUMERIC(18,6) NULL, accumulated_nav NUMERIC(18,6) NULL, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ, PRIMARY KEY(fund_id,nav_date))`; and `fund_sync_state(fund_id BIGINT REFERENCES fund(id), dataset VARCHAR(32), first_data_date DATE NULL, last_data_date DATE NULL, last_sync_at TIMESTAMPTZ NULL, last_sync_status VARCHAR(16), last_error TEXT NULL, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ, PRIMARY KEY(fund_id,dataset))`. Use only dataset `NAV_DAILY`. Fee fields may be read from the daily feed, but do not affect eligibility and are not stored in these v0.1 tables; add a channel/time-specific snapshot later only if needed. Upsert non-NULL full-history values (including corrected historical values) and fill stored NULLs with snapshot-only values; do not let a snapshot revise a stored non-NULL value, replace a non-NULL NAV with NULL, or delete a row because a response omits it. When both sources disagree, report the discrepancy and persist the historical value. One fund's NAV writes, metadata and SUCCESS sync state commit in one transaction; first/last dates are the min/max of stored observed rows, not coverage proof. For a failed eligible fund, roll back its data transaction and record FAILED, attempt time and sanitized error in a separate short transaction if DB access remains possible, without changing prior first/last dates. `fund.status` stays `ACTIVE` by default and does not track backfill failures. Alternative (a run-wide transaction) discards other funds' successes and impedes retry.
4. **Interfaces and operational boundary:** Provide a `backfill` CLI command: without `--code` it selects all current eligible candidates; with one or more `--code` arguments it selects only those supplied codes, subject to the same eligibility check. No `--all` flag is needed. Provide a read-only command-line query taking code, start date and end date inclusive, outputting ascending ISO dates, decimal strings and nullable NAV fields; an unknown code or empty range returns an empty result. Validate six-digit input codes and real date bounds; invalid inputs fail with a clear error. Process sequentially, releasing each fund's history after commit, and report per-fund outcomes, partial historical coverage, snapshot gap fills and dated/metric history-snapshot discrepancies, plus selection counts. Continue after a fund-level failure; exit nonzero if any eligible fund failed or selection itself failed. Prefer a CLI over an HTTP server for this one-off backfill and minimal query contract. Include a deployment script for the separately authorized Aliyun DB/app and instructions for the authorized new Git remote in the later implementation phase; do not perform Git, DB administration, or deployment in this artifact stage. Never schedule the CLI.

## Risks / Trade-offs

- [Name/daily feeds can omit or misclassify funds, and ETF/LOF spot feeds are unreachable] → Fail closed for required feed failures, report exclusions, and sample dual-open LOFs and ETFs including `166009`; eligibility may include exchange-traded funds and does not establish Alipay availability or verified off-exchange trading.
- [Provider floats, changing dated daily columns, missing indicators, rate limits] → Offline fixtures for response shapes, actual dated columns and precision, small live sampling before a full run, explicit per-fund errors and bounded sequential processing; no claim of source-decimal fidelity or full-history coverage from daily snapshots.
- [Numeric rounding, historical revisions, snapshot conflicts, partial dates] → Document HALF_UP, authoritative non-NULL historical revisions and reported same-date discrepancies; snapshots fill gaps only, preserve stored non-NULL values against snapshot changes, and do not treat min/max dates as contiguous coverage.
- [Database unavailable during failure recording] → Do not claim an outcome was persisted; return nonzero and report the DB error. Successful commits for other funds remain intact.
- [Deployment resource and credential constraints unverified] → Measure a small run and use a dedicated database role/secret injection; do not touch Ariadne or create a timer.

## Migration Plan

At `/opsx-apply`, implement offline tests and schema first; test against a disposable database, then sample live calls and verify size/time before a full backfill. Create the authorized independent Aliyun database/user and deploy application/script with securely injected credentials; push to the authorized new Git repository during implementation/deployment, not now. Rollback stops the unscheduled process and leaves the independent database intact for inspection or retry; schema/data removal is an explicit operator action, never an Ariadne migration.

## Open Questions

The exact AKShare 1.18.97 name/daily field names and dynamic dated NAV columns, deployment privileges, remote reachability, and live rate/size limits require fixture inspection and a small live verification before broad execution. These are validation gates, not a request for renewed authorization for the already approved Git/DB/deployment actions. If source schemas cannot support the conservative filter or dated snapshot parsing, stop instead of broadening eligibility or inventing dates.
