## Context

Current `backfill` selects the dual-open, known non-money-market intersection of `fund_name_em` and `fund_open_fund_daily_em`, fetches both full histories, writes metadata/NAV plus a success row in `fund_sync_state`, and separately writes a failure row on error. The CLI runs bundled `apply_schema` first; the SQL also recreates `fund_sync_state` if absent. The earlier unarchived backfill draft describes these old semantics and is superseded here wherever it conflicts. The interrupted run has roughly 2.27 million NAV rows; a host-wide OOM and long stall occurred on the roughly 1.6 GiB RAM / 2 GiB swap host shared with Ariadne and PostgreSQL. `vm.swappiness=0` is already set and is outside this change.

## Goals / Non-Goals

**Goals:** Safely retain existing fund/NAV data while reducing to two tables; skip work already at the explicit recovery threshold `2026-09-24`; retain no-target manual full re-fetch; preserve valid NAV and report live, auditable outcomes; constrain host risk.

**Non-Goals:** No proof of continuous history or actual NAV correctness from `MAX(nav_date)`, no date-filtered AKShare request, daily sync, timer, concurrency, Ariadne or fee changes, or hard in-process cancellation of arbitrary library calls.

## Decisions

1. **Target-date selection, not status:** Add optional `backfill --target-date YYYY-MM-DD`, parsed as a real calendar date (no implicit today). After the existing fail-closed eligibility selection, including for `--code`, read `MAX(fund_nav_daily.nav_date)` joined through `fund.code` for each selected code. If `MAX >= T`, emit `SKIPPED` before either historical request, with no DB writes. Absent fund/NAV, NULL max or max below T triggers both complete AKShare indicator requests. Without the flag, always fetch complete history as before. A failed lookup aborts the run, never counts as a skip. End the psycopg read transaction explicitly after lookup (commit/rollback or a short read-only transaction), before any fetch or fund write; do not keep an idle transaction during network I/O. `MAX` is a scheduling heuristic only: an old row at T may be partial/wrong and a newly attempted fund can remain below T. Ordinary `backfill --code` is the manual recheck path. Alternative: use the old success flag; rejected as a separate, non-coverage-based state with migration burden.

2. **Two-table persistence and safe migration:** Keep existing `fund` and `fund_nav_daily`, preserving keys, NAV precision, metadata, and independent DB. Remove the failure-state write path and success-state upsert; commit one fund's metadata and NAV upserts in one transaction. On fetch/validation/DB failure, roll back unfinished fund writes, leave any previous committed NAV untouched, report the failure in memory/logs only and continue when DB integrity allows; no empty failure-only fund row. Retain full-history non-NULL correction and snapshot fill-only upsert rules. Remove state-table creation from both bundled `001_fofoca.sql` and `apply_schema`/`init-db` paths; `init-db` must remain safe to rerun and must not implicitly drop tables. For existing deployments, take an independently restorable backup of `fund_sync_state` (and safeguard `fund`/`fund_nav_daily` with a verified independent DB backup), verify backup content/counts and DB target before an explicit one-time `DROP TABLE fund_sync_state` with no CASCADE; on missing table, migration is a no-op. If backup/verification/drop fails, stop instead of running a partial rollout. No data rewrite or drop of the two retained tables; rollback restores code without reintroducing the removed table, or restores the verified backup only by deliberate operator decision. Alternative: drop automatically in every `init-db`; rejected because initialization is repeatable and should not perform destructive operations.

3. **Missing historical cells:** Validate dates even on missing-value rows and detect duplicate dates before filtering. Treat actual historical `None`/pandas `NaN` NAV cells as absent; reject blank/malformed present NAV, infinity, zero/negative and `NUMERIC(18,6)` overflow. If both indicators have no usable NAV, fail despite snapshots; if only one lacks usable NAV, report partial coverage. Omit any date with no usable historical or valid dated snapshot metric, without erasing stored values. Preserve historical precedence and existing snapshot validation/at-most-two-actual-dates rule. Alternative: reject all missing history cells; rejected because a legitimate missing metric need not invalidate the other metric.

4. **Progress and fetch bounds:** Flush sanitized code/stage/start/skip/success/failure/timeout messages during the run; retain final structured report with target date (if any), selected, attempted, skipped, succeeded and failed, per-fund outcomes and a target-specific reconciliation of eligible codes whose stored max is still below T (including NULL), never calling the whole run complete merely because the process exited. Recheck persisted max after attempts for target reporting; classify failures and still-below-target separately without double-counting, and fail closed if reconciliation DB reads fail. A successful exit requires no attempted failures and, in target mode, no eligible fund still below T; skipped funds are not fresh successes. Inspect the installed AKShare version's actual HTTP call/timeout/retry paths for both indicators before implementing configurable finite connect/read bounds; test real hooks and identify whether limits are best-effort (e.g. DNS, library retry, parsing may evade them). Do not use detached per-request timeout threads, pretend to kill blocked fetches or time out SQL transactions. A hard external wall-clock limit, if necessary, is a manually controlled process/service boundary, and an abrupt kill may preclude a final report. Alternative: future timeout with continued worker threads; rejected due to overlapping fetches and RAM growth.

5. **Manual host operation:** One worker, one fund at a time. Use a manually started, non-restarting FOFoca-only service/process with measured conservative memory and outer elapsed-time limits; no timer. Verify host swap/memory/OOM and Ariadne/PostgreSQL health before, during and after; stop and investigate a new OOM, repeated fetch timeout or sustained stall, without auto-restart. Trial a few eligible `--code` cases above and below T, inspect DB dates, preserved NAV and live/final reports, then explicitly authorize the all-eligible run at `2026-09-24`. Alternative: parallelism or automatic replay; rejected for this shared low-RAM host.

## Risks / Trade-offs

- [A single late NAV date masks holes or stale values] → Label the threshold as a skip heuristic, report remaining dates and use no-target `--code` for manual review; do not claim full history from a max date.
- [Old SQL or old revision recreates the table after drop] → Update bundled SQL, runtime schema and deployment guidance together, validate repeated `init-db`, keep a verified backup and stop on unexpected schema drift.
- [An upstream call blocks despite transport timeouts; host OOM affects neighbors] → Check actual transport and retries, monitor live progress/host health, apply measured external process limits, stop manually with no restart; never promise an in-process hard bound.
- [A kill leaves no final report or a DB failure leaves uncertain outcome] → Re-query committed NAV maxima before the next manual attempt; never infer progress from logs alone.

## Migration Plan

Implement and test offline plus disposable-PostgreSQL cases, timeout/progress behavior and repeated two-table schema initialization; update English README and deployment runbook. Review diff, commit/push the tested revision to the authorized remote, and deploy without auto-running backfill. Verify independent DB identity and restorable backups including old state table and retained fund/NAV data; check backup counts, then explicitly drop only the old state table and verify schema and NAV counts before/after. Stop on any discrepancy. Verify no runtime schema path recreates it. Check resource headroom and neighboring service health, run the small manual target-date sample, reconcile persisted max and NAV content, then separately authorize the long run. Monitor progress, memory/swap/OOM and service health throughout; report every eligible code still below T and failures at the end. On rollback stop the manual run, preserve fund/NAV, and restore reviewed code/config compatible with the two-table schema; restore the saved old table only if deliberately returning to old code after validation, never silently on routine `init-db`.

## Open Questions

The installed AKShare version's actual HTTP timeout/retry hooks and whether they cover both indicator paths require inspection and a small measured trial. Select the host-specific memory and elapsed-time caps from measured headroom, not total RAM; if no reliable in-process fetch bound exists, document it as best-effort and rely on explicit external stop controls rather than claiming hard cancellation.
